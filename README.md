## Можливості

- Лексичний аналіз (Flex): ключові слова, ідентифікатори, числа, оператори, коментарі `//`, повідомлення про невідомі символи з номером рядка.
- Синтаксичний аналіз (Bison): граматика підмножини C з пріоритетами операторів, розв'язанням dangling else, повідомленнями про синтаксичні помилки.
- Побудова AST: єдиний універсальний тип вузла `Node`.
- Інтерпретатор (семантика): змінні, блочні області видимості, цикли, функції, рекурсія, помилки виконання.
- Генерація коду: трансляція AST у робочу програму на Python.
- Візуалізація: експорт AST у JSON і інтерактивне дерево в браузері (d3.js).

## Хід розробки по етапах

Проєкт розроблявся поетапно. Після кожного етапу існувала робоча програма, яку можна було перевірити.

### Етап 0. Середовище

Робота виконувалась у Windows через WSL (Ubuntu). Встановлено `flex 2.6.4`, `bison 3.8.2`, `gcc 15.2.0`. Проєкт розміщено у файловій системі Linux (`~/lab_3`), а не в `/mnt/c/...`, щоб компіляція була швидшою і не виникало проблем із правами доступу.

Загальна схема роботи:

```
текст програми -> [Flex: лексер] -> потік токенів -> [Bison: парсер] -> AST
                                                                         |
                                       +---------------------------------+
                                       v                v                v
                                 інтерпретатор    генератор Python   JSON для d3.js
```

### Етап 1. Лексер (Flex)

Файл `lexer.l` має три секції, розділені `%%`: оголошення, правила (регулярний вираз і дія), користувацький код.

Що важливо:

- Лексер повертає номер токена, а текст лексеми лежить у `yytext`. Значення токена (число чи ім'я) передається в парсер через `yylval`.
- Flex застосовує два правила вибору: спочатку **найдовший збіг**, а при однаковій довжині виграє **правило, записане раніше**. Тому `int` стає ключовим словом (правило записане вище за `ID`), а `integer` стає ідентифікатором (збіг довший). Так само `==` розпізнається як один токен, а не два `=`.
- Одно-символьні токени (`+`, `;`, `(`) повертаються як сам символ, у граматиці вони пишуться як `'+'`. Багатосимвольні (`==`, `if`) мають імена (`EQ`, `KW_IF`).
- Пробіли й коментарі «з'їдаються» правилами з порожньою дією.
- Невідомий символ ловиться правилом `.` і дає повідомлення з номером рядка (`%option yylineno`), лексер при цьому не зупиняється.

Перевірка: `echo 'int integer = 10;' | ./lexer` дає `KW_INT`, `ID 'integer'`, `ASSIGN`, `NUM`, `SEMI`.

### Етап 2. Парсер для арифметичних виразів (Bison)

Спочатку граматика обчислювала вирази одразу, без дерева. Токени тепер визначає Bison (`parser.tab.h`), лексер підключає цей файл.

Ключові елементи `parser.y`:

- `%union` описує типи значень символів: `num` (int), `str` (char*), пізніше `node` (Node*).
- `$$` це значення лівої частини правила, `$1`, `$2`, `$3` це значення символів правої частини.
- `%left`, `%right`, `%nonassoc` задають асоціативність, а порядок рядків задає пріоритет: що нижче, то вищий.
- `%prec UMINUS` дає правилу унарного мінуса пріоритет вигаданого токена, бо інакше воно отримало б пріоритет бінарного `-`.

**Експерименти з конфліктами.** Якщо закоментувати рядки з `%left`/`%right`, Bison видає десятки shift/reduce конфліктів. Команда `bison -Wcounterexamples parser.y` показує приклад: `expr '>' expr • EQ expr`. Крапка означає позицію парсера: вираз уже на стеку, далі йде оператор. Парсер не знає, що робити:

- **shift**: зсунути оператор, тоді праве піддерево згрупується першим;
- **reduce**: згорнути те, що на стеку, тоді згрупується ліве.

Пріоритети розв'язують це: якщо правило має вищий пріоритет за токен-lookahead, роблять reduce, якщо нижчий, то shift. При рівності вирішує асоціативність: `%left` дає reduce, `%right` дає shift. Тому `10 - 4 - 3 = 3` (ліва асоціативність), а з `%right` було б `10 - (4 - 3) = 9`.

Те саме з присвоєнням: без `%right '='` виникають конфлікти виду `ID '=' expr • '<' expr`, а з ним `a = b = 3` розбирається як `a = (b = 3)`.

### Етап 3. Побудова AST

Замість миттєвого обчислення дії тепер будують дерево. Єдиний тип вузла:

```c
typedef struct Node {
    NodeType type;       // тип вузла (BINOP, IF, ...)
    int num;             // значення для NUM
    char *str;           // ім'я змінної або оператор
    struct Node **kids;  // дочірні вузли
    int nkids, cap;
    int line;            // рядок у вихідному коді
} Node;
```

- `new_node` створює вузол, `add_kid` додає нащадка (масив зростає динамічно).
- Дерево будується **знизу вгору**: спочатку листки (`NUM`, `VAR`), потім їх підвішують до батьків. Це природно для висхідного розбору.
- Дужок у AST немає: правило `'(' expr ')'` просто повертає `$2`, а групування закодоване структурою дерева. Для `2 + 3 * 4` вузол `*` лежить глибше за `+`.
- AST відрізняється від дерева розбору: воно не містить службових нетерміналів і розділювачів.
- `free($1)` після `new_node` потрібен, бо лексер робить `strdup` для кожного ідентифікатора, а `new_node` копіює рядок ще раз.

### Етап 4. Розширення до Mini-C

Додано блоки, `if/else`, `while`, `for`, функції з параметрами, виклики, `return`. Нові типи вузлів: `BLOCK`, `IF`, `WHILE`, `FOR`, `RETURN`, `FUNC`, `PARAMS`, `CALL`, `ARGS`, `EMPTY`.

Особливості:

- **Dangling else.** У `if (a) if (b) x; else y;` не зрозуміло, до якого `if` належить `else`. У стані `... stmt • KW_ELSE` парсер може згорнути внутрішній `if` або зсунути `else`. Розв'язано двома рядками:
  ```
  %nonassoc LOWER_THAN_ELSE
  %nonassoc KW_ELSE
  ```
  і `%prec LOWER_THAN_ELSE` у правилі `if` без `else`. Токен `else` має вищий пріоритет, тому виграє shift, і `else` належить найближчому `if`, як у C. У дереві внутрішній `IF` має три дочірні вузли (умова, then, else), зовнішній лише два. Без цих рядків Bison повідомляє про один shift/reduce конфлікт на токені `KW_ELSE` (перевірено через `-Wcounterexamples`).
- **Виклик функції.** Правило `ID '(' arg_list ')'` перетворює вузол списку аргументів `ARGS` на вузол `CALL` (змінюється його тип і ім'я), тому аргументи стають прямими дітьми `CALL`.
- **Порожні частини `for`.** Для порожньої ініціалізації, умови чи кроку створюється вузол `EMPTY`, тож `FOR` завжди має рівно чотири дочірні вузли.
- Правила `program: /* порожньо */ | program external` утворюють лівий рекурсивний список, що для LALR ефективно (стек не росте).

### Етап 5. Інтерпретатор (семантика)

Файл `interp.c` рекурсивно обходить AST двома функціями:

- `eval(вузол, середовище)` обчислює вираз і повертає `int`;
- `exec(вузол, середовище)` виконує оператор; повертає 1, якщо виконався `return`. Цей прапорець «розмотує» вкладені цикли й блоки: кожен рівень бачить 1 і одразу виходить. Значення лежить у `ret_val`.

Області видимості: структура `Env` містить список змінних і посилання на батька. Пошук іде від внутрішнього середовища до зовнішнього. Кожен `BLOCK` створює нове середовище, тому внутрішній `int x = 20;` не змінює зовнішній `x = 10`.

Функції:

- Інтерпретація починається з **двох проходів**: спочатку реєструються всі функції, потім виконуються оператори верхнього рівня. Тому функцію можна викликати до її визначення в тексті.
- Кожен виклик створює нове середовище, батьком якого є **глобальне**, а не середовище викликача (лексична видимість). Завдяки цьому рекурсія працює: `n` на різних рівнях не змішуються.
- Аргументи обчислюються в середовищі того, хто викликає.
- Вбудована функція `print(x)` виводить число.
- Після виконання викликається `main`, і виводиться її результат.

Семантичні помилки (синтаксично код правильний, але хибний за змістом) виявляються під час виконання: невизначена змінна, ділення на нуль, невірна кількість аргументів. Синтаксичні помилки ловить парсер (`2 + ;`).

### Етап 6. Генерація коду на Python

`codegen.c` обходить те саме AST і друкує еквівалентну програму на Python. Відмінності між мовами, які враховує генератор:

| Mini-C | Python | Рішення |
|---|---|---|
| `int x = 5;` | `x = 5` | оголошення стає присвоєнням |
| `a = b = 3` (присвоєння як вираз) | немає | оператор `:=` |
| `a / b` (ціле ділення) | `a // b` | заміна оператора |
| `for (i; c; s) body` | немає | `i`, потім `while c:`, а `s` у кінці тіла |
| `x < y` дає 0 або 1 | дає True/False | обгортка `int(...)` |
| блок `{}` з власним `x` | блоків немає | перейменування змінної (`x_1`) |

Доказ коректності: програма, виконана інтерпретатором, і згенерований Python дають однаковий вивід (`20, 10, 101, 102, 103, main повернула: 0` для `scopes.c`; `main повернула: 120` для `factorial.c`).

### Етап 7. Візуалізація AST (d3.js)

## Теорія: як працює Yacc/Bison

**Розділення ролей.** Лексер працює з регулярними мовами (скінченний автомат) і не розуміє вкладеність, тобто не знає, що дужки мають бути парними. Парсер працює з контекстно-вільною граматикою, яка описує вкладені структури.

**LALR(1).** L: читання зліва направо. R: розбір будує правий вивід у зворотному порядку (згортки). 1: один токен випередження (lookahead). Це висхідний (bottom-up) розбір.

**Як працює парсер.** Bison з граматики будує таблиці ACTION і GOTO. Функція `yyparse` тримає стек пар «стан автомата + семантичне значення». На кожному кроці за станом на вершині й поточним токеном вона обирає дію:

- **shift**: покласти токен на стек і перейти в новий стан;
- **reduce**: замінити на стеку праву частину правила його лівою частиною (виконується семантична дія, `$$` обчислюється з `$1..$n`);
- **accept** або **error** (тоді викликається `yyerror`).

Семантичні дії виконуються саме в момент згортки, коли всі символи правої частини вже на стеку.

**LALR проти інших.** LR(1) має найбільші таблиці, бо стани розрізняються за lookahead. SLR простіший, але слабший, бо використовує множини FOLLOW. LALR зливає стани LR(1) з однаковим ядром: таблиці малі (як у SLR), потужність майже як у LR(1). Злиття теоретично може створити reduce/reduce конфлікти, яких у LR(1) не було.

**Конфлікти.**

- *Shift/reduce.* За замовчуванням Bison обирає shift і попереджає. Свідомо розв'язується пріоритетами й асоціативністю (`%left`, `%right`, `%nonassoc`, `%prec`): порівнюється пріоритет правила й токена, при рівності вирішує асоціативність.
- *Reduce/reduce.* Bison обирає правило, записане в граматиці раніше. Зазвичай це ознака помилки в граматиці, яку краще виправити, а не покладатися на це правило.

## Обмеження

- Єдиний тип даних: `int`.
- Немає масивів, вказівників, структур, рядків і препроцесора.
- Немає `break`, `continue`, `++`, `--`, `&&`, `||`, `!`.
- У `for` не можна оголошувати змінну в заголовку: пишіть `int i; for (i = 0; ...)`.
- Функція бачить лише глобальні змінні й власні параметри.
- У згенерованому Python блочна видимість імітується перейменуванням змінних, а не мовним механізмом.
- Візуалізація потребує підключення до інтернету для завантаження d3.js.
